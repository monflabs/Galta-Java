# Native Modules and Resolvers

Scripts load modules with `import` and `require()`. What those specifiers resolve to is decided by the *module resolvers* registered on the builder with `addModuleResolver()`. A resolver can serve JavaScript sources from memory, from the file system, or from classes transpiled at build time; it can also serve *native modules*, whose exports are built in Java. This page is about writing and registering resolvers; the syntax side is in the User's Guide under [Modules](/GaltaJS/UserGuide/Modules).

## The resolver interface

```java
public interface JSModuleResolver {
	public JSModuleDescriptor getModule(String name);
	public Stream<JSModuleDescriptor> getModules();
	public default JSModule loadModule(JSGlobalContext globalContext, String name);
	public default JSModule loadModule(JSGlobalContext globalContext, String name, Consumer<JSModule> earlyRegister);
}
```

A resolver answers `getModule(name)` with a `JSModuleDescriptor` (or `null` when it does not know the name); the descriptor then loads the actual `JSModule` for a given global context. Resolvers are consulted in registration order; the first non-null descriptor wins.

Always extend `modules/AbstractModuleResolver` rather than the interface. It makes `getModule` final and implements the specifier fallback: it tries `findModule(name)` and then `findModule(name + ".js")` (`EXTENSION = ".js"`), so `import x from 'lib'` finds `lib.js`. You implement:

```java
protected abstract JSModuleDescriptor findModule(String name);
public abstract Stream<JSModuleDescriptor> getModules();   // enumeration, may be Stream.empty()
```

`AbstractModuleResolver` also carries `isCommonJS()` / `setCommonJS(boolean)`: when true, every module served by this resolver is parsed as CommonJS (`module.exports`, `exports`, `require`) instead of an ES module.

```
JSModuleResolver
 `- AbstractModuleResolver                     (.js fallback, CommonJS flag)
     |- NativeModuleResolver                   (exports built in Java)
     |    `- library/node/NodeModuleResolver   ('fs', 'node:fs', 'fs/promises')
     `- ScriptModuleResolver                   (+ initModule(JSGlobalContext, JSScriptUnit))
         |- JSSourceModuleResolver             (JavaScript sources; interpreted or transpiled)
         |    |- JSMemoryModuleResolver        put(name, text)
         |    `- JSPathModuleResolver          (java.nio Path or FileSystem[, Charset])
         |         `- JSFileModuleResolver     (java.io.File root[, Charset])
         `- JSTranspiledModuleResolver         (env, ClassLoader, basePackage) - classes generated by the Maven plugin
```

## Script resolvers

```java
JSMemoryModuleResolver modules = new JSMemoryModuleResolver()
		.put("math", "export const PI = 3; export function twice(x) { return x * 2 } export default 'math-lib';")
		.put("app",  "import lib, { twice, PI } from 'math'; export const result = `${lib}:${twice(PI)}`;");
JSEnvironment env = JavaScriptEnvironment.newBuilder().addModuleResolver(modules).build();

assertEquals("math-lib:6", env.evaluateScript("import { result } from 'app'; result"));
assertEquals(3, env.evaluateScript("import * as m from 'math'; m.PI"));
```

Sample: `doc_examples/ModulesExamples.java` (`testInMemoryModules`, `testFileModules`, `testCommonJsModules`)

`JSFileModuleResolver(File root)` and `JSPathModuleResolver(Path root)` resolve specifiers against a root directory (relative specifiers such as `./lib.js` included). `JSSourceModuleResolver.initTranspiler(JSTranspilerOptions, ClassLoader, TargetFactory)` switches any source resolver to transpile-and-compile mode: each module is turned into Java, compiled in memory into the `TargetFactory` and loaded through a `FactoryClassLoader` (see [Execution Modes](/GaltaJS/UserGuide/ExecutionModes)). `JSTranspiledModuleResolver` serves classes that already exist on the class path, typically generated by the `js-transpiler-maven` plugin, looking them up as `basePackage + "." + moduleName`.

## Native modules

A native module has no JavaScript source: its default export and named exports are Java values. It is built from three pieces: `NativeModuleResolver` (a resolver whose descriptors are native), `NativeModuleDescriptor` (a descriptor that knows how to build the module) and `JSNativeModule`:

```java
public JSNativeModule(JSEnvironment env, JSModuleDescriptor descriptor, Object defaultExport, JSObject namedExports)
```

`defaultExport` backs `import d from '...'`, `namedExports` (a `JSObject` whose properties are the exports) backs `import { a, b } from '...'` and `import * as ns from '...'`. Either may be `null`.

Sample: `doc_examples/ModulesExamples.java` (`testNativeModuleImplementedInJava`)

```java
NativeModuleResolver resolver = new NativeModuleResolver() {
	@Override
	protected JSModuleDescriptor findModule(String name) {
		if(!name.equals("host:config")) {
			return null;
		}
		return new NativeModuleDescriptor(name) {
			@Override
			public JSModule loadModule(JSGlobalContext context) {
				JSEnvironment env = context.getEnvironment();
				Object defaultExport = "config-v1";
				JSObject namedExports = JSObject.of(env, "host", "galta", "version", 7);
				return new JSNativeModule(env, this, defaultExport, namedExports);
			}
		};
	}
	@Override
	public Stream<JSModuleDescriptor> getModules() {
		return Stream.empty();
	}
};
JSEnvironment env = JavaScriptEnvironment.newBuilder().addModuleResolver(resolver).build();
assertEquals("galta/7/config-v1",
		env.evaluateScript("import d, { host, version } from 'host:config'; `${host}/${version}/${d}`"));
```

`loadModule` receives the global context, so a native module can expose functions (`BaseMethod` instances) that use the context's executor or output stream, and can build a different module instance per context. Exports may be any JavaScript value, including `BaseMethod` functions and Java objects that have an [accessor](/GaltaJS/Extending/Accessors).

Importing a name that the module does not export is a `JSException` at link time, exactly as for a script module.

### Source-phase and bytes imports

Two `JSModuleDescriptor` hooks with defaults decide what `import source x from '...'` and `import x from '...' with { type: 'bytes' }` see (syntax and semantics in the [User's Guide](/GaltaJS/UserGuide/Modules)):

| Hook | Default | Overridden by |
|---|---|---|
| `String getModuleSourceText()` | `null` for a script descriptor (`isScript()` - a JavaScript module has no source-phase representation, so `import source` throws a `SyntaxError`); `"// native module: <name>\n"` for any other descriptor | `JSTranspiledModuleResolver`, which returns the pre-transpiled unit's retained source when the generated class carries one |
| `byte[] getBytes()` | The UTF-8 bytes of `getScript()` (or of `getModuleSourceText()` for a non-script descriptor) | `JSPathModuleResolver`/`JSFileModuleResolver`, which read the file as-is (binary files work) |

Neither hook loads or evaluates the module: a native descriptor can answer them without ever calling `loadModule`, and a script descriptor is only ever asked for its text/bytes, not parsed. Override `getModuleSourceText()` on a `NativeModuleDescriptor` to expose something more useful than the placeholder (a generated `.d.ts`, the Java class name, ...).

Sample: `doc_examples/ModulesExamples.java` (`testSourcePhaseAndBytesImports`)

## Registering resolvers from a library

A library packages its module together with its globals by adding the resolver in `configureEnvironment`, which runs before the environment is built:

```java
@Override
public void configureEnvironment(Builder builder) {
	builder.addModuleResolver(new JSMemoryModuleResolver()
			.put("greeting/format", "export const exclaim = s => s + '!';"));
}
```

Sample: `doc_examples/LibrariesExamples.java` (`testCustomLibrary`). `library/node/NodeLibrary` is the bundled example: its whole body is `builder.addModuleResolver(new NodeModuleResolver())`.

## Early registration and circular imports

`JSModuleResolver.loadModule(globalContext, name, Consumer<JSModule> earlyRegister)` exists for self-imports and import cycles. A script module is registered in the global context's module cache *before* its top-level body runs (`JSSourceModuleResolver` calls `earlyRegister.accept(unit)` between `createScript` and `initModule`), so a cycle reached from inside that body finds the same instance instead of recursing into a second load. The interpreted path honours this; `loadTranspiledModule()` does not yet (it constructs and immediately runs the class), which is why cyclic imports through the transpiled resolver are listed in [Known Gaps](/GaltaJS/KnownGaps). Native modules never run a body, so they are unaffected.

## The `JSModule` API

What a resolver returns, and what Java gets back from `JSGlobalContext.importModule(...)` or `JSScriptUnit.initModule(...)`:

| Method | Meaning |
|---|---|
| `getDefaultExport()`, `hasDefaultExport()`, `setDefaultExport(v)` | The `default` export |
| `getNamedExports()`, `ensureNamedExports()`, `addNamedExports(name, v)` | Named exports as a `JSObject` |
| `getExport(name)` | One export, `default` included |
| `getExportAccessor(name)` | A live binding (`VarAccessor`) to an export, what `import { x }` reads through |
| `getModuleNamespaceObject()` | The `import * as ns` object (cached, spec 9.4.6) |
| `getExportedNames(Set)`, `resolveExport(name, Set)` | Spec-shaped resolution used for `export * from` and re-exports |
| `addStarReExport(...)`, `addNamedReExport(...)` | Re-export plumbing used by script modules |
| `getDescriptor()`, `getEnvironment()` | Origin |

```java
JSInterpretedUnit unit = env.createScript(
		"export const version = 3; export default function greet(n) { return 'hi ' + n }",
		"lib.js", JSEnvironment.SCRIPT_MODULE);
JSGlobalContext ctx = new InterpretedGlobalRuntimeContext(env, env.createProgramExecutor());
JSModule module = unit.initModule(ctx, false);
assertEquals(3, module.getExport("version"));
assertEquals("hi you", ctx.value(module.getDefaultExport()).call("you").stringValue());
```

Sample: `doc_examples/ExecutingCodeExamples.java` (`testRunningAModuleUnit`)

## Gotchas

- Resolvers are tried in registration order; a resolver that answers non-null for everything shadows all later ones.
- `AbstractModuleResolver` appends `.js` when the plain name fails, so `findModule` may be called twice per specifier.
- Set `setCommonJS(true)` on the resolver that serves CommonJS files; the flag is per resolver, not per file, and `CommonJSLibrary` is still needed for the global `require`.
- A static `import` of a module that uses top-level `await` from a classic script root does not wait for it (`ReferenceError: Cannot access ... before initialization`); use `await import(...)` or make the root a module.
- `import.meta` is an empty object; there is no `url` property.
