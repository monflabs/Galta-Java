# Generating the Documentation

The documentation is a [docsify](https://docsify.js.org) site: plain Markdown
rendered in the browser, with no build step for the pages themselves. Editing a
`.md` file under `docs/` is the whole workflow for the guides.

Two parts of the published site are generated rather than written, and are not
checked in: the javadoc of every published module (`docs/api/`, linked from the
[API reference](/API)) and the browser build of the GaltaJS
[playground](playground/ ':ignore') (`docs/playground/*.jar`).

## Viewing it locally

From the repository root:

```sh
npx docsify-cli serve --port 3030 docs
```

then open [http://localhost:3030](http://localhost:3030). The server watches
the files, so a saved edit shows up on reload. With the docsify CLI installed
globally, `docsify serve --port 3030 docs` does the same thing.

To preview the complete site - with the API reference and the playground -
generate them first, then serve `docs/` the way GitHub Pages does:

```sh
./buildtools/build-site.sh     # javadoc -> docs/api/, playground -> docs/playground/
./serve-docs.sh                # http://localhost:3030/ (or ./serve-docs.sh <port>)
```

`build-site.sh` builds only the published modules and the playground (about a
minute; the long compliance suites are not built). `MVN=/path/to/mvn` selects
another Maven binary.

## How the site is published

`.github/workflows/publish-docs.yml` runs `buildtools/build-site.sh` and deploys
`docs/` to GitHub Pages (<https://monflabs.github.io/Galta-Java/>) on every push
to `master`, and on demand from the *Actions* tab. The site therefore always
matches `master`; releases do not publish it separately. See
[Documentation site](/BuildAndRelease#documentation-site) for the GitHub
setup.

### The API reference

`docs/API.md` links the javadoc of every module that `galta/galta-bom/pom.xml`
manages - the list of published modules. `build-site.sh` generates the javadoc
of exactly those modules and **fails if `API.md` and `galta-bom` disagree**, so
when a module is added to (or removed from) the published set:

1. add it to `galta-bom` (and, if it was not published before, remove it from
   the `excludeArtifacts` of the `central` profile - see
   [What is published](/BuildAndRelease#what-is-published));
2. add its row to `docs/API.md`, linking `api/<artifactId>/index.html` with
   `':ignore'` so docsify opens the static javadoc instead of looking for a
   markdown page.

### The playground

`docs/playground/index.html` runs the CheerpJ build of the playground
(`galta/parent-js/js-playground-cheerpj`) in the browser. CheerpJ maps `/app/`
to the root of the web server, so the page computes the jar's URL from its own
path: the same page works at `/playground/` locally and at
`/Galta-Java/playground/` on GitHub Pages. The CheerpJ loader version in that
page is kept in sync with the module's own `cheerpj/index.html`.

## How the site is wired

| File | Role |
|---|---|
| `docs/index.html` | The whole docsify configuration - theme, search, and the `alias` that maps every folder's `_sidebar.md` back to the single root one |
| `docs/_sidebar.md` | The one navigation tree for the entire site |
| `docs/README.md` | The home page, served at `/` |
| `docs/<Section>/README.md` | A section's landing page, served at `/<Section>/` |
| `docs/API.md` | The API reference: one javadoc link per published module |
| `docs/playground/index.html` | The browser playground (CheerpJ) |
| `docs/api/`, `docs/playground/*.jar` | Generated by `buildtools/build-site.sh`, gitignored |

Links between pages are site-absolute and carry no `.md` extension -
`/GaltaJS/UserGuide/Modules`, not `Modules.md` - so they resolve the same way
from any page.

## Adding a page

1. Create the `.md` file in the right folder under `docs/`.
2. Add one line to `docs/_sidebar.md`; nothing discovers pages automatically.
3. If the page documents an API, back its snippets with a test - see below.

## Keeping the samples honest

Every Java and JavaScript sample in the documentation is backed by a JUnit
test in a `doc_examples` package of the module it documents:

| Section | Samples | Run by |
|---|---|---|
| GaltaJS | `galta/parent-js/js/src/test/java/doc_examples` | `AllDocExamplesTests` |
| GaltaJSON core | `galta/parent-json/json-tests/src/test/java/doc_examples/json` | `AllJsonDocExamplesTests` |
| GaltaJSON add-on modules | `src/test/java/doc_examples/<module>` in each module | the module's `All*Tests` suite |
| Utilities | `galta/parent-utilities/utilities-tests/src/test/java/doc_examples/util` | `AllUtilDocExamplesTests` |
| File systems, Java compiler, test support | `src/test/java/doc_examples/<module>` in each module | the module's `All*Tests` suite |

Each suite runs on every build of its module. A sample that stops
compiling or stops producing the documented result fails the build rather
than rotting quietly on the page, so a documented behaviour change is caught
where it happens.

When adding or changing a sample, put the real assertion in the matching
`doc_examples` class and reference it from the page (`Sample:
doc_examples/ModulesExamples.java`), so a reader can find the executable
version of what they are looking at. A new `Examples` class must be added to
its module's suite, or it never runs.
